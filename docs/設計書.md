## 1. 目的

- V1（index.html 単一9,950行）を**機能ごとのファイル構成**に刷新し、今後の改修速度と安全性を上げる
- **マルチレベルリファラル**（n次パートナーが自分のパートナーを招待し、候補者をバケツリレーで上位へ送客する仕組み）を導入する
- UI/UXを一新する（デザインはPhase 4で3案提示→選択）

| 論点 | 決定 |

## 2. 用語

| 用語 | 意味 |
|---|---|
| フロント企業（フロント） | 自分が招待した1つ下の階層の企業。KANOAのフロント＝1次パートナー |
| アップライン企業（アップ） | 自分を招待した1つ上の階層の企業。KANOAにアップラインは存在しない |
| ライン | 階層の呼称。1次=Aライン、2次=Bライン、…、Zライン(26次)、AAライン(27次)…ZZライン |
| 企業コード | 階層の頭文字＋5桁連番。例: `A00001`（Aラインの1社目）、`B00013`（Bラインの13社目） |
| 送客 | フロントから来た候補者を、自分のアップラインへ上げる判断 |
| 見送り | フロントから来た候補者を、上げずに止める判断 |

### 階層と頭文字の対応

1次=A, 2次=B, … 26次=Z, 27次=AA, 28次=AB, … の順で機械的に採番する（Excelの列名と同じ規則）。上限は `ZZ99999`。実運用でここに届くことはないため、事実上無制限。

## 3. 全体アーキテクチャ

### 3.1 ディレクトリ構成（フロントエンド）

ビルドツールなし・フレームワークなし。素のHTML/CSS/JS（ES Modules）で構成し、`index.html` がすべてを束ねる。V1と同じく静的ホスティングでそのまま動く。

```
kanoa-partner-v2/
├── index.html                 # シェル（画面骨格とモジュール読み込みのみ。ロジックは持たない）
├── css/
│   ├── base.css               # リセット・変数（色/余白/フォント）・共通レイアウト
│   ├── components.css         # ボタン・カード・ドロワー・モーダル等の共通部品
│   └── views.css              # 画面固有スタイル
├── js/
│   ├── config.js              # Supabase URL/キー・定数
│   ├── supabase.js            # クライアント初期化・Realtime購読・接続健全性
│   ├── auth.js                # ログイン（KANOA=supabase.auth / パートナー=Edge Function）
│   ├── store.js               # 画面横断の状態（ログイン中企業・未読数など最小限）
│   ├── router.js              # ハッシュルーティング（#/candidates 等）と画面切替
│   ├── ui/
│   │   ├── components.js      # ドロワー・モーダル・トースト・確認ダイアログ
│   │   └── format.js          # 日付・金額・エスケープ等のユーティリティ
│   └── features/              # ★機能ごとに1フォルダ。V2の本体
│       ├── dashboard/         # ホーム（自分宛の判断待ち・未読・お知らせ）
│       ├── candidates/        # 候補者の登録・一覧・詳細ドロワー
│       ├── relay/             # 送客/見送りの判断・リレー履歴
│       ├── projects/          # 案件の登録・公開管理
│       ├── companies/         # フロント企業の一覧・管理（KANOAは全社ツリー）
│       ├── invites/           # 招待コード発行・受諾フロー
│       ├── chat/              # 連絡チャット（隣接企業間）
│       ├── invoices/          # 紹介料・請求（KANOA↔Aラインのみ）
│       ├── tasks/             # タスク
│       └── settings/          # 自社情報・パスワード変更・（KANOA）管理者設定
├── supabase/
│   ├── migrations/            # SQL（テーブル・RLS・インデックス）。番号順に適用
│   └── functions/             # Edge Functions（下記5.3）
└── docs/
    ├── 設計書.md              # 本書
    └── 移行計画.md            # V1→V2データ移行（Phase 4で詳細化）
```

**分割の原則**

- 各 feature は「自分のHTML断片・自分のDB問い合わせ・自分のイベント処理」を自分のフォルダ内で完結させる
- feature 間の連携は router 経由の画面遷移と、store 経由の最小限の共有状態のみ。**feature同士の直接import禁止**
- V1で起きた「ドロワー閉じで一覧が消える」型のバグ（同一idの影武者DOM）を根絶するため、**裏描画（silentRerender）方式は採用しない**。Realtimeの更新は各featureが自分の画面だけを部分再描画する

### 3.2 データフロー

V1の「全データをメモリに持って全テーブルをデバウンスupsert」方式は廃止。理由: マルチレベルでは各社が見られるデータはRLSで絞られるため、全量同期が成立しない。

- 各featureが必要なデータを必要な時にSupabaseへ問い合わせる（一覧=ページング、詳細=単発取得）
- 書き込みはその場でinsert/update→成否をUI反映（V1の `insertReferral` と同じ思想を全書き込みに適用）
- Realtime購読は「自分に関係する行」のみ（判断待ち候補者・自分宛メッセージ）。V1で実装済みの「受信実績がなければポーリング併用」の保険思想は移植する

## 4. データモデル（Supabase / PostgreSQL）

V1と同じSupabaseプロジェクト内に**新しいテーブル群**を作る（V1のテーブルはそのまま残し、切替まで両方が動く）。V1と名前が被らないよう、V2では英語名を刷新する。

### 4.1 companies（パートナー企業）← V1: agencies

| 列 | 型 | 説明 |
|---|---|---|
| id | uuid PK | |
| code | text UNIQUE | 企業コード（例 `A00001`）。Edge Functionが採番 |
| tier | int | 階層（1=Aライン）。code と常に整合 |
| parent_id | uuid FK→companies | アップライン企業。**1次パートナーは null**（アップ=KANOA） |
| name / contact / email / phone | text | 会社名・担当者・連絡先 |
| status | text | `active` / `suspended` / `pending`（招待未受諾） |
| pw_hash | text | ログイン用。**bcrypt**（V1のSHA-256固定saltから強化。移行時は旧hashを保持し初回ログインで再ハッシュ） |
| bank / license / special / source | | V1から引き継ぐ属性 |
| created_at / joined_at | timestamptz | |

- 木構造はこの1テーブルの `parent_id` だけで表現する（KANOAは行として持たない＝`parent_id null`が最上位）
- 「自分のフロント一覧」= `parent_id = 自社id`。「自分のアップ」= `parent_id` の1行

### 4.2 invites（招待コード）★新規

| 列 | 型 | 説明 |
|---|---|---|
| id | uuid PK | |
| issued_by | uuid FK→companies **null可** | 発行企業。nullはKANOA発行（=Aライン招待） |
| code | text UNIQUE | 発行時に自動採番した企業コード（受諾時にそのままcompanies.codeになる） |
| temp_password | — | **DBに平文保存しない**。発行時に自動生成し、hashのみ保存。平文は発行画面に一度だけ表示 |
| company_name | text | 招待先の会社名（発行時に入力） |
| status | text | `issued` / `accepted` / `revoked` / `expired` |
| issued_at / accepted_at / expires_at | timestamptz | 有効期限は既定14日 |

招待フロー: 発行→「ログインURL＋企業コード＋初期パスワード」の定型文をワンタップコピー→相手に送る（メール/LINEは各社の手段で）→相手が初回ログイン→会社情報の確認＋パスワード変更を強制→`companies` 行が `active` に。

### 4.3 candidates（候補者）← V1: referrals + intake を統合

V1は「intake（パートナー申請）→KANOAが承認→referrals（正式送客）」の2テーブル2段階だった。V2はマルチレベルのリレーが本質なので、**候補者は1テーブル＋判断履歴**に統一する。

| 列 | 型 | 説明 |
|---|---|---|
| id | uuid PK | |
| name / kana / phone / email / address / area | text | 候補者情報 |
| project_id | uuid FK null可 | 希望案件（未定でも登録可） |
| registered_by | uuid FK→companies | 最初に登録した企業 |
| holder_id | uuid FK→companies **null可** | **今、判断権を持つ企業**。null=KANOAに到着済み |
| stage | text | `relay`（リレー中）/ `screening`（KANOA選考中）/ `rejected`（途中見送り）/ `closed` |
| status | text | KANOA到着後の選考ステータス（V1のstatus体系を継承: 確認中/面談設定/内定/入社…） |
| joined_on / resigned / spi_status / compliance_status など | | V1 referralsの選考管理列を継承 |
| note | text | 申し送り（リレーで引き継がれる） |
| created_at | timestamptz | |

**リレーの動き（例: Cライン C00002 が登録した場合）**

```
登録:  registered_by=C00002, holder=B00001(Cのアップ), stage=relay
  ↓ B00001 が「送客」
       holder=A00003(Bのアップ), stage=relay
  ↓ A00003 が「送客」
       holder=null（KANOA到着）, stage=screening → 以後はV1と同じ選考管理
  ※どこかで「見送り」→ stage=rejected, holder=見送った企業のまま保持（記録用）
```

### 4.4 candidate_steps（リレー判断履歴）★新規

| 列 | 型 | 説明 |
|---|---|---|
| id | uuid PK | |
| candidate_id | uuid FK | |
| company_id | uuid FK null可 | 判断した企業（null=KANOA） |
| action | text | `registered` / `forwarded`（送客）/ `rejected`（見送り）/ `accepted`（KANOA受入） |
| note | text | 判断時のコメント（任意） |
| created_at | timestamptz | |

「この候補者がどこを通って、どこで何日止まったか」を後から追える。V1のreflog（操作ログ）の役割も選考フェーズではこのテーブルに統合。

### 4.5 projects / project_shares（案件と公開範囲）

- **projects**: V1の列構成をほぼ継承（求人票・報酬・選考フロー・詳細JSON）。作成はKANOAのみ
- **project_shares** ← V1: assignments を置換

| 列 | 型 | 説明 |
|---|---|---|
| project_id / company_id | 複合PK | |
| shared_by | uuid null可 | 共有した企業（null=KANOA） |
| published | bool | |

案件の見え方: KANOAがAラインへ公開するのはV1と同じ。**加えて、案件を見られる企業は自分のフロントへ「共有」できる**（フロントの候補者募集に案件情報が必要なため）。報酬額の上書き（V1のref_override等）はKANOA→Aラインの共有にのみ存在（紹介料がそこにしか発生しないため）。

### 4.6 messages（連絡チャット）← V1: messages

スレッド = **企業とそのアップラインの1対1**（Aラインの相手はKANOA）。V1の「agency_idごとのスレッド」を「company_idごとのスレッド＝その企業とアップの会話」へ一般化するだけで、構造はV1を継承。

| 列 | 型 | 説明 |
|---|---|---|
| id / company_id / sender / body | | sender: `up`（アップ側）/ `self`（企業側） |
| candidate_id | uuid null可 | 候補者カードに紐づく会話（V1のref_id相当） |
| reply_to / reactions / mentions / stamp / pinned / edited / deleted / read | | V1の機能を全て継承（[[連絡チャットシステム 再現プロンプト]]準拠） |

### 4.7 その他（V1構造をほぼそのまま継承）

- **invoices**: KANOA↔Aラインのみ。V1の列構成・ステータス遷移を継承
- **documents**: 候補者の書類。candidate_id に付け替え
- **tasks / members / login_logs / kanoa_admins**: V1を継承（tasksのagency_id→company_id等の改名のみ）

## 5. 認証・権限

### 5.1 ログイン（V1の方式を継承・強化）

- **KANOA管理者**: supabase.auth（メール＋パスワード）
- **パートナー**: 共通ログイン画面で企業コード＋パスワード → Edge Function `partner-login` がbcrypt照合し、`company_id` と `tier` をクレームに持つJWTを発行。全パートナーが同一UI・同一ログイン画面
- V1にあった「Edge Function未配備時のクライアント側フォールバック」は**廃止**（V1でも既に無効化済み。V2では最初からEdge Function前提）

### 5.2 RLS（行レベルセキュリティ）の基本方針

JWTの `company_id` を基点に、**「自分」「自分のアップ」「自分のフロント」の3方向だけ**が見える世界を作る。

| テーブル | パートナーが見られる範囲 |
|---|---|
| companies | 自社・自分のフロント各社（アップは名前のみのビュー経由） |
| candidates | 自分が登録した候補者＋**holder_id=自社**（判断待ち）＋自分のフロントが登録し自分を通過した候補者 |
| candidate_steps | 見られる候補者に紐づく行 |
| projects / project_shares | 自社に共有された案件 |
| messages | company_id=自社 のスレッド＋自分のフロント各社とのスレッド |
| invoices | 自社宛（Aラインのみ） |

KANOA管理者は全テーブル全行（service相当のポリシー）。**書き込みも同様にRLSで制限**し、「送客」操作はDB内のトランザクション関数（RPC `v2_relay_decide`）経由でのみ holder を書き換える（クライアントから任意のholder書き換えを許さない。関数内で権限確認→holder付替え→履歴追記までを1トランザクションで行うため、途中で切れて中途半端になることがない）。

### 5.3 Edge Functions

| 関数 | 役割 |
|---|---|
| partner-login | 企業コード＋パスワード照合→JWT発行（レート制限つき。V1から継承） |
| invite-issue | 企業コード採番＋初期パスワード生成＋invites行作成（採番の同時実行対策はDB側のシーケンスで担保） |
| invite-accept | 初回ログイン→companies行作成＋本パスワード設定 |

送客/見送り・候補者登録・企業コード採番は、Edge FunctionではなくPostgreSQL関数（RPC: `v2_relay_decide` / `v2_register_candidate` / `v2_next_code`）で実装する。DB内で完結するためトランザクション保証があり、可動部品も少ない。

## 7. V1データ移行（Phase 4で `移行計画.md` として詳細化）

| V1 | → V2 | 備考 |
|---|---|---|

| invoices / documents / tasks / members | 同名 | idそのまま、FK名読み替え |

## 9. 設計上の申し送り（V1の教訓の反映）

1. **同一idの影武者DOMを作らない**（2026-07-23のドロワーバグの根本原因。V2は部分再描画方式で構造的に排除）
2. **複数ロール共有の保存処理は要素存在ガード必須**（2026-07-22の知見。V2はfeature分割でフォーム自体を分けて構造的に排除)
3. **Realtimeは「受信実績」を信用の条件にし、保険ポーリングを併設**（V1の実装思想を継承）
4. **一意制約エラー（電話番号重複等）はその場でinsertして検知**（一括同期に任せない。V2は全書き込みがこの方式）
